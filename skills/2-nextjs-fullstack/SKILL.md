# Next.js Fullstack HunaSuna

## Цель

Помогать строить HunaSuna как Next.js fullstack-проект, где web-версия и будущее мобильное приложение используют один backend, одну базу данных и одни правила безопасности.

## Основные правила

- Использовать Next.js как основу проекта.
- Для первой версии делать backend через Route Handlers в `app/api`.
- Использовать Better Auth для авторизации.
- Использовать Prisma ORM для работы с PostgreSQL.
- Использовать Tailwind CSS и shadcn/ui для интерфейса.
- Использовать Vercel Cron Jobs для фоновых задач.
- Не держать бизнес-логику прямо в route-файлах.
- Выносить основную логику в `server/services`.
- Проверку доступа и авторизацию держать на backend.
- Делать API пригодным и для сайта, и для будущего мобильного приложения.

## Рекомендуемая структура

- `app` - страницы и маршруты Next.js.
- `app/api` - API endpoints.
- `server/services` - бизнес-логика.
- `server/db` - работа с базой данных.
- `server/auth` - авторизация и проверка доступа.
- `server/validators` - проверка входящих данных.
- `server/jobs` - фоновые задачи.
- `server/sms` - отправка SMS-кодов.
- `server/logs` - технические логи безопасности.
- `components` - интерфейсные компоненты.
- `lib` - общие помощники.

## Backend HunaSuna должен уметь

- регистрировать пользователя;
- подтверждать мобильный номер SMS-кодом;
- выполнять вход;
- восстанавливать пароль;
- работать с личным кабинетом;
- хранить контакты;
- хранить записи;
- искать по контакту, дате и номеру телефона;
- переносить записи в раздел “Удаленные”;
- восстанавливать удаленные записи в течение 7 дней;
- скрывать архивные записи от обычного пользователя;
- хранить архивные записи администрации 3 месяца;
- ограничивать отправку SMS-кодов: не больше 3 SMS за 10 минут на один номер или IP-адрес;
- проверять, что пользователь видит только свои данные.

## API

Основные группы API:

- `/api/auth`
- `/api/auth/verify-phone`
- `/api/users/me`
- `/api/settings` - пароль, имя, фамилия, email и мобильный номер
- `/api/contacts`
- `/api/records`
- `/api/deleted-records`
- `/api/search`

Каждый endpoint должен проверять:

- пользователь вошел в аккаунт;
- аккаунт подтвержден;
- данные принадлежат текущему пользователю;
- входящие данные корректные.

## Мобильное приложение

Не писать логику так, чтобы она работала только внутри web-страниц.

Вся важная логика должна быть доступна через API, чтобы позже мобильное приложение могло использовать те же аккаунты, контакты, записи, поиск и раздел “Удаленные”.

## Проверка качества

Перед завершением задачи проверять:

- нет ли бизнес-логики, спрятанной только в интерфейсе;
- не отдает ли API чужие данные;
- не раскрывает ли API лишние поля;
- можно ли использовать этот же endpoint из мобильного приложения;
- не добавляет ли API удаление аккаунта в первую версию;
- понятны ли ошибки пользователю.
