# Завершенный план: подготовка спецификаций проекта

## Назначение

Этот документ фиксирует, что было сделано на этапе начальной подготовки проекта HunaSuna.

Этап завершен как подготовка основной документации: проект получил понятные границы, продуктовые правила, технические решения и структуру первой версии.

## Что было сделано

### 1. Зафиксировали назначение проекта

Было описано, что HunaSuna - это инструмент учета информации о переводах.

Важно: проект не переводит деньги, не хранит деньги и не является банком, обменником, кошельком, платежной системой или финансовым посредником.

### 2. Описали продуктовые границы

Были зафиксированы правила первой версии:

- использовать слово “запись”, а не “тикет”;
- не добавлять реальные денежные переводы;
- не добавлять платежи;
- не добавлять банковские карты;
- не добавлять кошельки;
- не добавлять балансы;
- не добавлять комиссии;
- не добавлять автоматический курс валют;
- не добавлять удаление аккаунта в первую версию;
- не добавлять сложную аналитику и командные роли.

### 3. Описали функции первой версии

Были описаны основные функции:

- регистрация;
- вход;
- восстановление доступа;
- личный кабинет;
- контакты;
- записи;
- история;
- поиск;
- удаленные записи;
- восстановление удаленной записи в течение 7 дней.

### 4. Описали пользовательские сценарии

Были подготовлены сценарии:

- новый пользователь регистрируется;
- пользователь входит в аккаунт;
- пользователь добавляет контакт;
- пользователь создает запись;
- пользователь находит старую запись;
- пользователь редактирует запись;
- пользователь удаляет запись;
- пользователь восстанавливает запись;
- пользователь меняет данные в личном кабинете;
- пользователь выходит из аккаунта.

### 5. Описали данные проекта

Была зафиксирована модель данных:

- пользователь;
- контакт;
- запись;
- код восстановления;
- технический лог безопасности;
- архивная запись.

Для записи было отдельно зафиксировано, что нужно хранить снимок данных отправителя и получателя на момент создания записи.

### 6. Описали правила безопасности

Были зафиксированы правила:

- каждый пользователь видит только свои данные;
- пароли нельзя хранить обычным текстом;
- мобильный номер можно хранить в аккаунте без SMS-подтверждения;
- после 5 неправильных попыток входа попытки блокируются на 30 минут;
- удаленную запись нельзя редактировать;
- архив администрации доступен только технически.

### 7. Выбрали технические решения

Были выбраны основные технологии первой версии:

- Next.js;
- Route Handlers в `app/api`;
- PostgreSQL;
- Prisma;
- собственная session-cookie авторизация как решение первой версии;
- Tailwind CSS и shadcn/ui;
- Vercel для хостинга;
- Vercel Cron Jobs для фоновых задач.

### 8. Описали структуру проекта

Была описана структура:

- `app`;
- `app/api`;
- `components`;
- `server/services`;
- `server/db`;
- `server/auth`;
- `server/validators`;
- `server/jobs`;
- `server/logs`;
- `lib`;
- `prisma`;
- `specification`;
- `skills`.

### 9. Добавили правила оптимизации

Были описаны правила:

- списки загружать частями;
- API должен отдавать только нужные поля;
- использовать пагинацию;
- добавить индексы под основные запросы;
- фоновые задачи выполнять батчами;
- не показывать архивные записи обычному пользователю;
- не кэшировать личные данные публично.

### 10. Подготовили рабочие скилы

В папке `skills/` были добавлены инструкции для разных направлений:

- спеки проекта;
- Next.js fullstack;
- база данных;
- безопасность и авторизация;
- интерфейс.

## Результат

Начальная подготовка проекта завершена.

Проект получил основную карту, продуктовые границы, технические решения, структуру, правила безопасности и план первой версии.

## Важно для будущей работы

Спеки остаются главным источником правды. Если код или новые планы расходятся со спеками, сначала нужно показать противоречие пользователю и предложить точное исправление.
