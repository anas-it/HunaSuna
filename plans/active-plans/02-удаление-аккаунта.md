# План удаления аккаунта HunaSuna

## Статус

План активный.

Цель: добавить удаление собственного аккаунта пользователя на web-сайте и в мобильном приложении HunaSuna через личный кабинет/настройки, с проверкой секретного вопроса и ответа.

Прогресс:

- 2026-06-16: web-настройки `/settings`, server action и `DELETE /api/users/me` реализованы для удаления только текущего аккаунта через секретный ответ и подтверждающую фразу.
- Осталось: mobile-экран удаления аккаунта, privacy-страница и финальные App Store Review Notes.

## Почему это нужно

Удаление аккаунта добавляется в первую web/mobile версию как узкая функция приватности и требование App Store. Apple требует, чтобы приложения с созданием аккаунта позволяли пользователю инициировать удаление аккаунта внутри приложения.

Официальный источник Apple: https://developer.apple.com/support/offering-account-deletion-in-your-app/

Важные правила Apple:

- опция удаления должна быть легко найдена, обычно в настройках аккаунта;
- нужно предлагать удаление всего аккаунта и связанных персональных данных, если нет законной причины хранить часть данных;
- можно добавить повторную проверку личности и подтверждение, чтобы аккаунт не удалили случайно;
- если удаление занимает время, пользователь должен видеть понятное объяснение.

## Главное продуктово-техническое решение

Делать не ручной запрос через email, а встроенное удаление аккаунта в личном кабинете web и в настройках mobile.

Причина: HunaSuna не является сильно регулируемой финансовой системой. Apple прямо предупреждает, что для обычных приложений не стоит заставлять пользователя звонить, писать email или проходить долгий support-flow, если аккаунт можно удалить в приложении.

## Пользовательский сценарий

1. Пользователь входит в свой аккаунт.
2. Открывает личный кабинет:
   - web: `/settings`;
   - mobile: экран `Настройки`.
3. Видит отдельный раздел `Удаление аккаунта`.
4. Открывает раздел и видит предупреждение:
   - аккаунт будет удален;
   - контакты, записи, удаленные записи, архивные записи и сессии будут удалены из пользовательской базы;
   - действие нельзя отменить;
   - технические логи и резервные копии могут храниться ограниченное время для безопасности и обслуживания.
5. Видит свой секретный вопрос.
6. Вводит секретный ответ.
7. Вводит подтверждающую фразу, например `УДАЛИТЬ АККАУНТ`.
8. Нажимает красную кнопку `Удалить аккаунт`.
9. Backend проверяет текущую сессию и секретный ответ.
10. Если все верно, backend удаляет только аккаунт текущего пользователя.
11. Все сессии этого пользователя закрываются.
12. Web перенаправляет на страницу входа.
13. Mobile очищает SecureStore/session token и возвращает пользователя на экран входа.

## Правила доступа

- Клиент никогда не отправляет `userId` для удаления аккаунта.
- Backend берет пользователя только из текущей web cookie или mobile bearer token.
- Endpoint удаляет только `currentUser.id`.
- Нельзя удалить чужой аккаунт через параметр URL, body или query.
- Не добавлять admin endpoint для удаления аккаунтов в первой версии.
- Если пользователь не вошел, endpoint возвращает `401`.

## Проверка секретного вопроса

Использовать существующую логику секретного ответа:

- секретный вопрос показывается только владельцу текущего аккаунта в личном кабинете;
- секретный ответ не показывается никогда;
- введенный ответ нормализуется так же, как при восстановлении пароля: `trim().toLowerCase()`;
- проверка идет через `verifyPassword` против `secretAnswerHash`;
- после 5 неправильных ответов блокировать попытку удаления аккаунта на 30 минут для пары аккаунт + IP.

Для блокировки можно переиспользовать `LoginAttempt` с target:

```text
account-delete:<userId>
```

## API

Добавить:

```text
DELETE /api/users/me
```

Тело запроса:

```json
{
  "secretAnswer": "ответ пользователя",
  "confirmation": "УДАЛИТЬ АККАУНТ"
}
```

Успешный ответ:

```json
{
  "ok": true
}
```

Ошибки:

```json
{
  "ok": false,
  "message": "Неверный секретный ответ"
}
```

Почему лучше `DELETE /api/users/me`, а не `DELETE /api/users/:id`: в URL нет чужого id, и сама форма endpoint подчеркивает, что действие относится только к текущему пользователю.

### Сервис

Добавить в `Web-Project/server/services/user.service.ts` функцию:

```text
deleteCurrentUserAccount(userId, input, meta)
```

Функция должна:

1. Валидировать `secretAnswer` и `confirmation`.
2. Найти пользователя по `userId`.
3. Проверить, что у пользователя есть `secretQuestion` и `secretAnswerHash`.
4. Проверить лимит неправильных попыток.
5. Проверить секретный ответ.
6. При неверном ответе записать неудачную попытку и security log.
7. При верном ответе выполнить транзакцию:
   - записать security log `account_deleted`;
   - удалить login attempts, связанные с этим пользователем и его login/email/phone targets;
   - удалить пользователя.

Текущая Prisma-схема уже помогает каскадно удалить:

- `UserSession` через `onDelete: Cascade`;
- `Contact` через `onDelete: Cascade`;
- `Record` через `onDelete: Cascade`;
- `ArchivedRecord` через `onDelete: Cascade`.

`SecurityLog` и `LoginAttempt` сейчас имеют `onDelete: SetNull`. Для приватности лучше:

- `LoginAttempt` по известным targets удалить явно;
- `SecurityLog` оставить только как техническое событие без email, телефона, логина и секретных данных в metadata.

### SecurityLog

Добавить actions:

```text
account_delete_failed
account_deleted
```

В metadata не писать секретный ответ, email, телефон, логин или имя пользователя.

## Данные и удаление

Удаление аккаунта должно удалить из основной базы пользовательские данные:

- аккаунт;
- session tokens;
- контакты;
- записи;
- удаленные записи;
- архивные записи;
- связи записей с контактами.

Что может остаться:

- обезличенные технические security logs без userId после `onDelete: SetNull`;
- резервные копии до технического срока хранения.

Политика конфиденциальности должна честно объяснять этот момент.

## Тестовый аккаунт для Apple Review

Перед отправкой в App Store создать отдельный тестовый аккаунт:

- login: отдельный тестовый login;
- password: отдельный тестовый password;
- secret question: простой вопрос для ревью;
- secret answer: отдельный тестовый ответ.

В App Review Information указать secret answer только если Apple должна проверить удаление аккаунта.

## Ручная проверка web

1. Создать тестовый аккаунт.
2. Войти на сайт.
3. Открыть `/settings`.
4. Проверить, что виден раздел `Удаление аккаунта`.
5. Ввести неверный секретный ответ.
6. Убедиться, что аккаунт не удален.
7. Ввести верный секретный ответ и неверную подтверждающую фразу.
8. Убедиться, что аккаунт не удален.
9. Ввести верный секретный ответ и `УДАЛИТЬ АККАУНТ`.
10. Убедиться, что произошел logout и вход старым логином больше невозможен.
11. Убедиться, что чужие аккаунты и их данные не затронуты.

## Ручная проверка mobile

1. Войти в mobile под тестовым аккаунтом.
2. Открыть `Настройки`.
3. Открыть `Удаление аккаунта`.
4. Проверить неверный ответ и понятную ошибку.
5. Проверить успешное удаление.
6. Убедиться, что SecureStore очищен и приложение вернулось на экран входа.
7. Убедиться, что старый token больше не открывает API.

## Критерии готовности

План считается выполненным, когда:

- спеки синхронизированы и больше не запрещают это App Store/privacy исключение;
- web позволяет удалить только текущий аккаунт из `/settings`;
- mobile позволяет удалить только текущий аккаунт из `Настройки`;
- удаление требует секретный вопрос/ответ и подтверждающую фразу;
- неверные секретные ответы ограничиваются после 5 попыток на 30 минут;
- после удаления пользовательские session tokens закрыты;
- пользовательские контакты, записи и архивные записи удаляются из основной базы;
- политика конфиденциальности обновлена;
- App Store listing/review notes обновлены;
- проверки TypeScript/lint/build или их доступный минимум пройдены.
