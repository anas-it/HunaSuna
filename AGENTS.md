# AGENTS HunaSuna

## Назначение

Этот файл объясняет, как AI-агент должен работать с проектом HunaSuna.

HunaSuna - это инструмент учета информации о переводах. Проект не переводит деньги, не хранит деньги и не является банком, обменником, платежной системой или финансовым посредником.

## Главные источники правды

Перед важными изменениями читать:

- `specification/global-specs/00-project-overview.md` - краткая карта проекта;
- `specification/README.md` - карта групп спецификаций и главных источников правды;
- `specification/` - основные спеки проекта;
- `specification/planning-specs/11-development-plan.md` - порядок разработки первой версии;
- `specification/technical-specs/12-technical-decisions.md` - выбранные технологии первой версии;
- `specification/technical-specs/13-project-structure.md` - структура будущего кода;
- `plans/active-plans/` - рабочие планы будущей и текущей разработки;
- `plans/completed-plans/` - выполненные планы и описания уже сделанных этапов;
- `CHANGELOG.md` - журнал заметных изменений проекта;
- `skills/` - рабочие скилы для разных направлений.

Если между файлами есть противоречие, сначала показать проблему пользователю и предложить точное исправление.

## Как отвечать пользователю

- Писать на русском языке.
- Объяснять простыми словами.
- Не усложнять без необходимости.
- Если пользователь просит “проверь” - только анализировать и не менять файлы.
- Если пользователь просит “сохрани”, “исправь” или “добавь” - вносить изменения в файлы.
- Если пользователь просит “не меняй” - не редактировать файлы.
- Не менять смысл текста пользователя без причины.

## Продуктовые правила

- На сайте использовать слово “запись”, а не “тикет”.
- Описывать проект как учет информации о переводах.
- Не добавлять реальные платежи, балансы, карты, кошельки, комиссии или обмен денег в первую версию.
- Удаление аккаунта входит в первую web/mobile версию только как функция приватности и требование App Store.
- Пользователь может удалить только свой текущий аккаунт, в котором он вошел.
- Для подтверждения удаления аккаунта пользователь должен ответить на свой секретный вопрос: увидеть вопрос и ввести секретный ответ.
- Удаление аккаунта не является финансовой функцией и не добавляет платежи, балансы, кошельки, карты, комиссии или реальные денежные переводы.
- Первая версия должна быть простой, удобной и без лишних функций.
- Все решения должны учитывать будущую мобильную версию.

## Технические правила

- Основной framework - Next.js.
- Backend первой версии - Route Handlers Next.js в `app/api`.
- Бизнес-логику выносить в `server/services`.
- Работу с базой держать отдельно от интерфейса.
- API проектировать так, чтобы его могла использовать web-версия и будущее мобильное приложение.
- База данных - PostgreSQL.
- ORM - Prisma.
- Авторизация первой версии - собственная session-cookie авторизация через `UserSession` и httpOnly cookie.
- UI - Tailwind CSS и shadcn/ui.
- Для локальной разработки база данных работает на PostgreSQL на компьютере разработчика.
- Для будущего деплоя базы данных можно использовать Neon PostgreSQL.
- Хостинг сайта - Vercel.
- Фоновые задачи - Vercel Cron Jobs.

## Данные и безопасность

- Каждый пользователь видит только свои данные.
- Пароли нельзя хранить обычным текстом.
- Мобильный номер можно хранить в аккаунте, но SMS-подтверждение в первой версии не используется.
- Логин уникален и ищется без учета регистра: `ADMINpro` и `adminpro` считаются одним логином.
- Восстановление пароля в первой версии работает только через секретный вопрос и ответ.
- Email, SMS и временные коды восстановления пароля в первой версии не используются.
- После 5 неправильных попыток входа блокировать попытки на 30 минут.
- Пользователь может менять в личном кабинете пароль, имя, фамилию, email и мобильный номер.
- Пользователь может удалить в личном кабинете только свой аккаунт; для удаления нужно ответить на секретный вопрос.
- Сумма и курс сохраняются так, как их указал пользователь, без специальных ограничений формата в первой версии.
- Дата и время определяются по IP-адресу пользователя.
- Поиск работает по контакту и номеру телефона; поиск по дате в первой версии не делаем.
- Удаленная запись хранится в разделе “Удаленные” 7 дней.
- Пока запись удалена, ее нельзя редактировать.
- После 7 дней запись исчезает из пользовательского интерфейса окончательно, но остается в техническом архиве базы данных без пользовательского доступа.
- Доступ к архиву администрации в первой версии только технический.

## Работа со спеками

При проверке спека искать:

- незаполненные разделы;
- противоречия;
- серые зоны;
- лишние функции для первой версии;
- риски безопасности;
- риски, из-за которых сайт может выглядеть как сервис денежных переводов.

При изменении спека синхронизировать связанные места в других спеках.

## Работа с планами

- Спеки проекта хранить в `specification/`, даже если в названии спека есть слово “план”.
- Все рабочие планы будущей и текущей разработки хранить в `plans/active-plans/`.
- Все выполненные планы и описания уже сделанных этапов хранить в `plans/completed-plans/`.
- Если пользователь просит составить рабочий план по проекту, агент должен сразу сохранить этот план в `plans/active-plans/`, если пользователь прямо не попросил не менять файлы.
- Не оставлять рабочий план только в сообщении чата: файл плана в `plans/active-plans/` является рабочим источником правды для дальнейшей работы.
- Один и тот же план не должен одновременно лежать в активных и завершенных.
- Когда все пункты активного плана выполнены, агент должен автоматически перенести план из `plans/active-plans/` в `plans/completed-plans/`.
- При создании нового активного плана обновлять `plans/active-plans/README.md`, если там ведется список текущих планов.
- При переносе плана в завершенные обновлять `plans/active-plans/README.md` и `plans/completed-plans/README.md`.
- При создании, переносе или завершении плана обновлять `CHANGELOG.md`, если изменение важно для истории проекта.
- Если путь к плану упоминается в спеках, скилах или `AGENTS.md`, обновлять эти ссылки вместе с переносом.

## Работа с кодом

Когда начнется разработка:

- сначала читать структуру проекта;
- следовать существующему стилю;
- не делать большие рефакторы без необходимости;
- проверять изменения тестами или минимальной ручной проверкой;
- не трогать чужие изменения без просьбы пользователя.
