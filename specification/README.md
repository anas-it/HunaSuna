# Карта спецификаций HunaSuna

Этот файл нужен как навигация по `specification/`. Он не заменяет сами спеки, а объясняет, какой документ за что отвечает.

Главная проблема, которую решает этот README: по старым названиям файлов не всегда сразу видно, где глобальные правила проекта, где продуктовые функции, где технические решения, где mobile-only спеки, а где план. Поэтому до переименования файлов используем эту карту как безопасный реестр.

## Как читать спеки

Если нужно быстро понять проект:

1. Читать `00-обзор-проекта.md`.
2. Читать этот `README.md`.
3. По задаче выбрать нужный тип спека из таблицы ниже.
4. Если есть конфликт между спеками, не исправлять молча: сначала показать конфликт пользователю и предложить точное решение.

## Почему пока не переименовываем файлы автоматически

Переименование безопасно только тогда, когда вместе с ним обновлены все ссылки в:

- `AGENTS.md`;
- `specification/`;
- `skills/`;
- `активные планы/`;
- `завершенные планы/`;
- `CHANGELOG.md`;
- коде, если где-то есть ссылки на документацию.

Поэтому текущий безопасный шаг - добавить карту типов и правила переименования. После проверки человеком можно делать `git mv`.

## Как безопасно переименовывать

1. Убедиться, что рабочая папка чистая:

   ```powershell
   git status --short
   ```

2. Переименовывать только через `git mv`, например:

   ```powershell
   git mv specification/09-технический.md specification/tech-09-архитектура.md
   ```

3. Найти все старые ссылки:

   ```powershell
   rg "09-технический|specification/09-технический"
   ```

4. Обновить ссылки в `AGENTS.md`, `skills/`, `specification/`, планах и `CHANGELOG.md`, если они там есть.

5. Проверить, что старых ссылок не осталось:

   ```powershell
   rg "09-технический|specification/09-технический"
   ```

6. Проверить проект:

   ```powershell
   npm run lint
   npm run build
   cd mobile
   npx tsc --noEmit
   ```

7. Делать отдельный коммит только на переименование и обновление ссылок:

   ```powershell
   git add -A
   git commit -m "Organize specification filenames"
   ```

8. Не смешивать переименование с изменением смысла спека. Сначала переименование, потом отдельным коммитом правки содержания.

## Что не нужно делать

- Не переносить постоянные спеки в `активные планы/` или `завершенные планы/`.
- Не хранить рабочие планы в `specification/`, кроме постоянного `11-план-разработки.md`.
- Не менять названия файлов вручную через проводник без обновления ссылок.
- Не делать массовое переименование без проверки `rg`.
- Не менять смысл спека только ради нового названия.
