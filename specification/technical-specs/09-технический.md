# Технический HunaSuna

## Назначение документа

Этот документ описывает техническую основу HunaSuna: из каких частей будет состоять сайт и какие технические решения нужно учитывать при разработке.

## Frontend
Frontend HunaSuna должен быть сделан на Next.js.

Интерфейс должен быть удобным для браузера на компьютере и адаптированным под мобильный экран.

Основные страницы:

- страница приветствия;
- регистрация;
- вход;
- личный кабинет;
- главная;
- контакты;
- создание записи;
- история записей;
- раздел “Удаленные”;
- настройки.


## Backend
Backend HunaSuna должен быть частью Next.js-приложения.

Для первой версии backend нужно делать через Route Handlers Next.js в папке `app/api`.

Route Handlers должны только принимать запрос, проверять пользователя, вызывать нужную бизнес-логику и возвращать ответ.

Основную бизнес-логику нельзя держать прямо в route-файлах. Ее нужно вынести в отдельный server/service слой.

Рекомендуемая структура backend:

- `app/api` - публичные API endpoints для сайта и будущего мобильного приложения;
- `server/services` - бизнес-логика HunaSuna;
- `server/db` - работа с базой данных;
- `server/auth` - авторизация, сессии, проверка доступа;
- `server/validators` - проверка входящих данных;
- `server/jobs` - фоновые задачи, например очистка удаленных записей.

Backend отвечает за:

- регистрацию пользователей;
- вход в аккаунт;
- восстановление пароля;
- личный кабинет и настройки;
- контакты;
- записи;
- поиск;
- раздел “Удаленные”;
- восстановление удаленных записей в течение 7 дней;
- автоматическое удаление записей из пользовательского интерфейса через 7 дней;
- технический архив и резервные копии для администрации;
- проверку, что пользователь видит только свои данные.

Backend должен быть построен так, чтобы мобильное приложение могло использовать те же API, ту же базу данных и те же правила безопасности.


## База данных
В базе данных запись должна хранить связь с контактом и снимок данных на момент создания записи.

Для отправителя нужны технические поля:

- sender_contact_id;
- sender_first_name_snapshot;
- sender_last_name_snapshot;
- sender_phone_snapshot.

Для получателя нужны технические поля:

- receiver_contact_id;
- receiver_first_name_snapshot;
- receiver_last_name_snapshot;
- receiver_phone_snapshot.

Если пользователь выбрал контакт, в записи сохраняется id контакта и снимок имени, фамилии и номера телефона.

Если пользователь ввел данные вручную, id контакта остается пустым, а имя, фамилия и номер телефона сохраняются как снимок.

Если контакт позже изменен или удален, старая запись не должна изменяться.

Номер телефона при ручном вводе отправителя или получателя необязателен. Если номер не указан, соответствующее snapshot-поле номера телефона остается пустым.

Сумма и курс сохраняются так, как их указал пользователь. В первой версии специальных ограничений по формату суммы и курса нет.

Дата и время записи добавляются автоматически. Часовой пояс нужно определять по IP-адресу пользователя и сохранять вместе с записью.


## Авторизация
При регистрации пользователь указывает логин, пароль и данные восстановления.

Мобильный номер можно хранить в аккаунте, но SMS-подтверждение в первой версии не используется.

Проект не подключает Twilio Verify или Vonage Verify.

Восстановление пароля в первой версии работает только через секретный вопрос и ответ.

Секретный ответ хранится только в защищенном виде.

После 5 неправильных секретных ответов восстановление блокируется на 30 минут для этого IP-адреса и логина.

SMS-коды, email-коды и временные коды восстановления в первой версии не используются.

Web-версия использует httpOnly cookie. Мобильное приложение использует тот же `UserSession`, но передает session token через заголовок `Authorization: Bearer <token>`.


## API
API должен быть единым для web-версии и будущего мобильного приложения.

Основные группы API:

- `/api/auth` - регистрация, вход, выход, восстановление пароля;
- `/api/users/me` - данные текущего пользователя;
- `/api/settings` - изменение пароля, имени, фамилии, email и мобильного номера;
- `/api/contacts` - добавление, просмотр, редактирование и удаление контактов;
- `/api/records` - создание, просмотр, редактирование и удаление записей;
- `/api/deleted-records` - просмотр и восстановление удаленных записей;
- `/api/search` - поиск по контакту и номеру телефона.

Каждый API endpoint должен проверять:

- пользователь вошел в аккаунт;
- пользователь имеет доступ только к своим данным;
- входящие данные корректные.

API не должен отдавать лишние поля. Клиент должен получать только те данные, которые нужны для интерфейса.

Списки API должны поддерживать пагинацию через `page` и `limit`. Ответ должен возвращать данные текущей страницы и информацию о пагинации.

Подробный формат API для web и мобильного приложения описан в `specification/technical-specs/16-api-contract.md`.


## Хранение данных
Все данные пользователя должны быть связаны с id пользователя.

Один пользователь не должен видеть данные другого пользователя.

Пароли нельзя хранить обычным текстом.

Записи должны хранить снимок данных отправителя и получателя на момент создания записи.

Удаленные записи должны находиться в разделе “Удаленные” 7 дней.

После 7 дней запись исчезает из пользовательского интерфейса окончательно, но может оставаться в техническом архиве базы данных и резервных копиях администрации.

Архивные записи остаются в техническом архиве базы данных без пользовательского доступа. Срок хранения резервных копий задается отдельно политикой инфраструктуры.

Доступ к архиву администрации в первой версии должен быть только технический, без отдельной админ-панели.


## Поиск
Поиск должен работать по:

- контакту;
- номеру телефона.

Поиск должен искать только внутри данных текущего пользователя.

Поиск по дате в первой версии не делаем.

Если номер телефона не указан вручную, поиск по номеру такую запись не найдет.

Поиск не должен показывать записи, которые уже окончательно исчезли из пользовательского интерфейса.

Поиск должен использовать лимиты списков и не должен загружать все найденные записи сразу.

## Оптимизация и производительность

Подробные правила оптимизации описаны в `specification/technical-specs/14-оптимизация.md`.

Основные требования:

- списки записей, контактов, удаленных записей и истории контакта должны иметь пагинацию;
- API должен отдавать короткие ответы для списков;
- база данных должна иметь индексы под основные запросы;
- фоновые задачи должны работать батчами;
- личные данные пользователя нельзя кэшировать публично.


## Восстановление удаленных записей
Удаленная запись находится в разделе “Удаленные” 7 дней.

В течение 7 дней пользователь может восстановить запись.

Пока запись находится в разделе “Удаленные”, пользователь не может ее редактировать.

Если прошло 7 дней и пользователь не восстановил запись, запись должна исчезнуть из пользовательского интерфейса окончательно.

После этого запись может оставаться в техническом архиве базы данных и резервных копиях администрации сайта.

Архивная запись не должна возвращаться в обычный пользовательский интерфейс и не должна быть доступна пользователю через поиск, историю, контакты или раздел “Удаленные”.

Архивные записи остаются в техническом архиве базы данных без пользовательского доступа. Срок хранения резервных копий задается отдельно политикой инфраструктуры.

Удаление аккаунта пользователя в первой версии не реализуется.


## Подготовка к мобильному приложению
HunaSuna должен проектироваться так, чтобы мобильное приложение не требовало нового backend.

Мобильное приложение должно использовать:

- те же аккаунты;
- те же контакты;
- те же записи;
- тот же раздел “Удаленные”;
- ту же авторизацию;
- те же API endpoints;
- ту же базу данных.

Подробные правила мобильной версии описаны в `specification/mobile-specs/15-мобильное-приложение.md` и `specification/mobile-specs/17-мобильная-безопасность.md`.

Все бизнес-правила должны находиться на backend, а не только в интерфейсе сайта. Тогда web-версия и мобильное приложение будут работать одинаково.

Нельзя завязывать логику только на страницы Next.js. Важная логика должна быть в server/service слое, который можно использовать из API.


## Деплой
Для первой версии нужен простой и надежный деплой.

Подходящий вариант:

- Next.js-приложение на Vercel или другом хостинге с поддержкой Next.js;
- PostgreSQL в облаке;
- HTTPS обязательно.

Перед запуском нужно настроить:

- переменные окружения;
- подключение к базе данных;
- секреты для авторизации;
- резервные копии базы данных.

Для европейских пользователей серверные функции и база данных должны быть размещены рядом. Основной регион Vercel для первой версии - Frankfurt, `fra1`. Если используется Neon PostgreSQL, базу нужно создавать в европейском регионе, чтобы разделы сайта не ждали долгие сетевые запросы к базе.


## Мониторинг и ошибки
Backend должен логировать ошибки и важные действия.

Нужно логировать:

- вход в аккаунт;
- неправильные попытки входа;
- восстановление пароля;
- создание записи;
- редактирование записи;
- удаление записи;
- восстановление записи;
- изменение пароля;
- изменение email;
- изменение мобильного номера.

Пользователю ошибки нужно показывать простым текстом.

Технические ошибки не должны показывать пользователю внутренние детали системы, базу данных, stack trace или секреты.
