# API-контракт HunaSuna

## Назначение документа

Этот документ фиксирует единый API-контракт для web-версии и мобильного приложения HunaSuna.

API должен быть общим. Отдельный backend только для мобильного приложения в первой версии не нужен.

## Общие правила

Все API endpoints возвращают JSON.

Успешный ответ:

```json
{
  "ok": true
}
```

Ответ с ошибкой:

```json
{
  "ok": false,
  "message": "Понятный текст ошибки"
}
```

API не должен возвращать stack trace, SQL, внутренние секреты или лишние поля пользователя.

## Авторизация

Web-версия использует httpOnly cookie `hunasuna_session`.

Мобильное приложение использует тот же `UserSession`, но передает session token в заголовке:

```text
Authorization: Bearer <session token>
```

Backend хранит только хеш session token.

Backend определяет часовой пояс по IP через инфраструктурные заголовки `x-vercel-ip-timezone` или `cf-timezone`. Клиентский заголовок с timezone не используется, чтобы сайт, мобильная web-версия и приложение работали по одному правилу.

Если IP-timezone недоступен или некорректен, backend использует безопасный fallback `UTC`.

Если пользователь не вошел, защищенный endpoint возвращает `401`:

```json
{
  "ok": false,
  "message": "Нужно войти в аккаунт"
}
```

## Мобильная сессия

Для получения мобильной сессии клиент при регистрации или входе передает:

```json
{
  "client": "mobile"
}
```

или заголовок:

```text
x-hunasuna-client: mobile
```

В ответе backend добавляет:

```json
{
  "ok": true,
  "user": {},
  "session": {
    "token": "session-token",
    "expiresAt": "2026-07-04T00:00:00.000Z"
  }
}
```

Web-клиент не должен использовать `session.token` и продолжает работать через cookie.

Native mobile app хранит `session.token` только в защищенном хранилище устройства, например Expo SecureStore. Expo Web/dev web preview может использовать `sessionStorage` только для тестирования. Production web-сайт работает через httpOnly cookie и не хранит bearer token в браузерном JavaScript.

## `/api/auth`

`POST /api/auth`

Поддерживаемые действия:

- `register` - регистрация;
- `login` - вход;
- `logout` - выход;
- `request-password-recovery` - получить секретный вопрос;
- `reset-password` - сбросить пароль через секретный ответ.

Восстановление пароля работает только через секретный вопрос и ответ. SMS-коды, email-коды и временные коды не используются.

После 5 неправильных секретных ответов восстановление для этого IP-адреса и логина блокируется на 30 минут.

При регистрации обязательны `login`, `password`, `confirmPassword`, `secretQuestion` и `secretAnswer`. Поля `phone` и `email` необязательные: пользователь может указать телефон, email, оба значения или не указывать их.

## `/api/users/me`

`GET /api/users/me`

Возвращает данные текущего пользователя.

Endpoint должен работать и с cookie, и с bearer session token.

`DELETE /api/users/me`

Удаляет только аккаунт текущего пользователя, определенного по web cookie или mobile bearer token. Клиент не передает `userId` удаляемого аккаунта.

Тело запроса:

```json
{
  "secretAnswer": "ответ пользователя",
  "confirmation": "УДАЛИТЬ АККАУНТ"
}
```

Backend должен проверить текущую сессию, секретный ответ пользователя и подтверждающую фразу. После 5 неправильных секретных ответов попытки удаления аккаунта блокируются на 30 минут для этого пользователя и IP-адреса.

Удаление аккаунта входит в первую web/mobile версию только как функция приватности и требование App Store. Оно не является финансовой функцией и не добавляет платежи, балансы, кошельки, карты, комиссии или реальные денежные переводы.

## `/api/settings`

`PATCH /api/settings`

Поддерживаемые действия:

- `profile` - изменить имя, фамилию или мобильный номер;
- `password` - изменить пароль с текущим паролем;
- `email` - изменить email;
- `reveal-sensitive` - показать чувствительные данные после проверки текущего пароля.

Пароль нельзя менять через действие `profile`.

## `/api/contacts`

Контакты:

- `GET /api/contacts` - список контактов;
- `POST /api/contacts` - создать контакт;
- `GET /api/contacts/:id` - открыть контакт;
- `PATCH /api/contacts/:id` - изменить контакт;
- `DELETE /api/contacts/:id` - удалить контакт.

Каждый запрос должен ограничиваться текущим пользователем.

`GET /api/contacts` может принимать `query`, чтобы мобильное приложение показывало подсказки контактов по началу имени, фамилии или номеру телефона.

## `/api/records`

Записи:

- `GET /api/records` - список записей;
- `POST /api/records` - создать запись;
- `GET /api/records/:id` - открыть запись;
- `PATCH /api/records/:id` - изменить запись;
- `DELETE /api/records/:id` - удалить запись.

Удаленную запись нельзя редактировать, пока она не восстановлена.

## `/api/deleted-records`

Удаленные записи:

- `GET /api/deleted-records` - список удаленных записей;
- `POST /api/deleted-records/:id/restore` - восстановить запись.

Пользователь может восстановить только свою запись и только в течение 7 дней.

## `/api/search`

`GET /api/search`

Поиск первой версии работает только по:

- контакту;
- номеру телефона.

Поиск по дате в первой версии не делаем.

## Пагинация

Списки принимают:

- `page`;
- `limit`.

Ответ списка должен возвращать данные текущей страницы и информацию о пагинации.

API не должен загружать все записи пользователя одним запросом.

## Cron endpoints

Cron endpoints не предназначены для мобильного приложения.

`/api/cron/*` должен быть защищен `CRON_SECRET` и не должен принимать пользовательскую bearer-сессию как доступ к техническим задачам.
