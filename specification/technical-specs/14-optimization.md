# Оптимизация HunaSuna

## Назначение документа

Этот документ описывает, какие оптимизации нужны HunaSuna для первой версии и будущего роста проекта.

Оптимизация не должна добавлять лишние функции и не должна делать сайт похожим на банк, обменник, кошелек или платежную систему. HunaSuna остается инструментом учета информации о переводах.

## Главный принцип

Сначала нужно оптимизировать простые и важные места:

- скорость загрузки списков;
- размер API-ответов;
- стабильность фоновых задач;
- безопасность пользовательских данных;
- предсказуемую работу базы данных;
- готовность backend к будущему мобильному приложению.

Не нужно добавлять сложные технологии без реальной необходимости. Если проблему можно решить лимитом, пагинацией, индексом или коротким API-ответом, нужно выбрать простой вариант.

## Предусловия перед глубокой оптимизацией

Перед глубокой оптимизацией нужно закрыть важные расхождения со спеками первой версии:

- регистрация не должна зависеть от SMS-подтверждения;
- API должен проверять, что пользователь вошел;
- собственная session-cookie авторизация должна быть явно зафиксирована в спеках как решение первой версии.

Эти пункты важнее тонкой оптимизации скорости, потому что они влияют на безопасность и соответствие первой версии.

## Пагинация списков

Все большие списки должны загружаться частями.

Для первой версии используются такие лимиты:

- записи: 15 записей на страницу;
- максимум записей за один запрос: 50;
- контакты: 50 контактов на страницу;
- максимум контактов за один запрос: 100;
- история контакта: 15 записей на страницу;
- удаленные записи: 15 записей на страницу.

API должен принимать `page` и `limit`. Если параметры не указаны, используются стандартные лимиты.

Нельзя загружать все записи пользователя одним запросом.

## API-ответы

API не должен отдавать лишние поля.

Для списков записей достаточно отдавать:

- id;
- дату;
- данные отправителя;
- данные получателя;
- сумму;
- валюту;
- курс;
- часовой пояс;
- дату восстановления, если запись удалена.

Полные данные записи можно отдавать только для просмотра или редактирования одной записи.

Ответы списков должны возвращать:

- данные текущей страницы;
- номер текущей страницы;
- лимит;
- общее количество записей;
- количество страниц;
- есть ли следующая страница;
- есть ли предыдущая страница.

## Оптимизация базы данных

Индексы должны соответствовать главным запросам первой версии:

- активные записи пользователя по дате;
- удаленные записи пользователя;
- история записей по контакту;
- поиск по номеру телефона;
- контакты пользователя по имени и фамилии;
- архивирование удаленных записей после 7 дней;
- архивирование удаленных записей без пользовательского доступа.

Перед добавлением сложных индексов нужно проверять реальные запросы на тестовых данных.

## Поиск

Поиск первой версии работает только по:

- контакту;
- номеру телефона.

Поиск по дате и фильтр по валюте в первой версии не добавлять.

Поиск всегда должен ограничиваться `userId` текущего пользователя.

Поиск через частичное совпадение можно оставить для первой версии. Если база станет большой, нужно отдельно проверить скорость поиска и при необходимости добавить нормализованные поисковые поля или PostgreSQL full-text/trigram-подход.

## Фоновые задачи

Фоновые задачи должны работать батчами.

Правила:

- за один запуск обрабатывать ограниченное количество записей;
- не загружать все истекшие записи сразу;
- повторный запуск не должен создавать дубли архива;
- результат выполнения должен показывать, сколько записей обработано;
- ошибки не должны раскрывать пользователю внутренние детали системы.

Рекомендуемый размер батча для первой версии: 100 записей.

## Интерфейс

Интерфейс должен оставаться простым.

Для списков нужно:

- показывать только одну страницу данных;
- делать основную сортировку по дате на сервере;
- использовать клиентскую сортировку только для уже загруженной страницы;
- не делать мелкие кнопки пагинации;
- сохранять понятные пустые состояния.

Если контактов станет много, длинный выбор контакта в форме записи нужно заменить на поиск контакта.

## Кэширование

Пользовательские страницы и API с личными данными нельзя кэшировать публично.

Можно кэшировать только безопасные статические данные:

- список поддерживаемых валют;
- статические страницы без личных данных;
- общие ресурсы интерфейса.

Нельзя допустить, чтобы один пользователь получил данные другого пользователя из кэша.

## Регион сервера и базы данных

Для пользователей в Европе серверные страницы, API и база данных должны находиться как можно ближе друг к другу.

Для деплоя на Vercel основной регион первой версии: Frankfurt, `fra1`.

Если база данных находится в Neon PostgreSQL, проект базы нужно создавать в европейском регионе, например Frankfurt или ближайшем доступном регионе. Нельзя размещать сайт в Европе, а базу данных в США без причины: каждый раздел будет ждать сетевой запрос через океан.

Если все разделы сайта медленно открываются из Австрии или другой европейской страны, сначала проверить:

- регион Vercel Functions;
- регион базы PostgreSQL;
- холодный старт serverless-функций;
- время ответа API `/api/records` и `/api/contacts`;
- количество запросов к базе на открытие раздела.

## Метрики качества

Перед релизом нужно проверять:

- `npm run lint`;
- `npm run build`;
- базовые сценарии регистрации, входа, контактов, записей, поиска, удаления и восстановления;
- что API не отдает лишние поля;
- что списки не загружают больше разрешенного лимита;
- что фоновые задачи не обрабатывают все записи сразу;
- что архивные записи не отображаются обычному пользователю.

## Что не оптимизировать в первой версии

В первой версии не нужно добавлять:

- сложную аналитику;
- автоматические курсы валют;
- платежные статусы;
- кошельки, балансы, карты;
- отдельный backend для мобильного приложения;
- внешний поисковый сервис без реальной необходимости;
- сложную систему ролей.
