# План разработки HunaSuna

## Назначение документа

Этот документ описывает порядок разработки первой версии HunaSuna после завершения основных спецификаций.

Цель плана - идти по шагам и не добавлять лишние функции раньше времени.

## Главный принцип разработки

Сначала нужно сделать простую рабочую версию, где пользователь может зарегистрироваться, войти, добавить контакты, создать запись, найти ее, отредактировать, удалить и восстановить в течение 7 дней, а также удалить свой аккаунт как функцию приватности и требование App Store.

HunaSuna должен оставаться инструментом учета информации, а не сервисом денежных переводов.

## Техническая основа

Проект строится на:

- Next.js;
- Route Handlers в `Web-Project/app/api`;
- PostgreSQL;
- `Web-Project/server/services` для бизнес-логики.

Backend нужно строить так, чтобы мобильная версия могла использовать те же API, аккаунты, контакты, записи и правила безопасности.

## Основные папки проекта

Рекомендуемая структура:

- `Web-Project/app` - страницы и маршруты Next.js;
- `Web-Project/app/api` - API endpoints;
- `Web-Project/components` - интерфейсные компоненты;
- `Web-Project/server/services` - бизнес-логика;
- `Web-Project/server/db` - работа с базой данных;
- `Web-Project/server/auth` - авторизация и доступ;
- `Web-Project/server/validators` - проверка данных;
- `Web-Project/server/jobs` - фоновые задачи;
- `Web-Project/lib` - общие помощники;
- `Mobile-App` - мобильное приложение;
- `plans/active-plans` - планы проекта в работе;
- `plans/completed-plans` - уже выполненные планы проекта;
- `CHANGELOG.md` - журнал заметных изменений проекта.

## Основные страницы

Для первой версии нужны страницы:

- приветствие или входная страница;
- регистрация;
- вход;
- восстановление пароля;
- главная после входа;
- контакты;
- просмотр контакта;
- создание записи;
- просмотр записи;
- история записей;
- поиск;
- удаленные записи;
- личный кабинет и настройки.

## Основные API

Нужны API группы:

- `/api/auth` - регистрация, вход, выход, восстановление пароля;
- `/api/users/me` - данные текущего пользователя и удаление собственного аккаунта;
- `/api/settings` - изменение пароля, имени, фамилии, email и мобильного номера;
- `/api/contacts` - контакты;
- `/api/records` - записи;
- `/api/deleted-records` - удаленные записи и восстановление;
- `/api/search` - поиск по контакту и номеру телефона.

Каждый API endpoint должен проверять пользователя, доступ к данным и корректность входящих данных.

## Основные таблицы базы данных

Для первой версии нужны таблицы или модели:

- `User`;
- `UserSession`;
- `LoginAttempt`;
- `Contact`;
- `Record`;
- `SecurityLog`;
- `ArchivedRecord`.

Восстановление пароля хранится в полях пользователя: секретный вопрос и защищенный хеш секретного ответа. Отдельная таблица кодов восстановления в первой версии не нужна.

Записи должны хранить связь с контактом и снимок данных отправителя и получателя на момент создания записи.

Удаленные записи до 7 дней можно хранить в `records` через поля удаления:

- `deleted_at`;
- `restore_until`;
- `archived_at`.

После 7 дней запись исчезает из пользовательского интерфейса окончательно и может быть перенесена или скопирована в `archived_records`.

Архив `archived_records` доступен только технически и хранит данные в техническом архиве базы данных без пользовательского доступа.

## Порядок разработки

### Шаг 1: Подготовка проекта

- создать Next.js проект;
- настроить TypeScript, если он используется;
- настроить базовую структуру папок;
- настроить базовые стили интерфейса;
- подключить GitHub.

### Шаг 2: База данных

- выбрать способ работы с PostgreSQL;
- создать модели пользователя, контакта и записи;
- добавить поля для удаленных записей;
- добавить поля для снимков отправителя и получателя;
- подготовить миграции.

### Шаг 3: Регистрация и вход

- сделать регистрацию;
- сделать вход;
- сделать выход;
- добавить защиту от неправильных попыток входа.

### Шаг 4: Личный кабинет

- показать данные пользователя;
- дать возможность изменить пароль;
- дать возможность изменить имя и фамилию;
- дать возможность изменить email;
- дать возможность изменить мобильный номер.
- дать возможность удалить свой аккаунт после ответа на секретный вопрос.

Удаление аккаунта входит в первую web/mobile версию только как функция приватности и требование App Store. Пользователь может удалить только аккаунт, в котором он сейчас вошел. Удаление аккаунта не является финансовой функцией и не добавляет платежи, балансы, кошельки, карты, комиссии или реальные денежные переводы.

### Шаг 5: Контакты

- создать список контактов;
- добавить создание контакта;
- добавить редактирование контакта;
- добавить удаление контакта;
- сделать просмотр контакта и истории записей по нему.

Если контакт удален, старые записи не должны меняться.

### Шаг 6: Записи

- создать форму записи;
- дать выбор контакта или ручной ввод имени, фамилии и номера телефона;
- сохранить сумму, валюту и курс так, как их указал пользователь;
- автоматически сохранять дату и время по IP-адресу пользователя;
- сохранять снимок данных отправителя и получателя.

### Шаг 7: История и поиск

- показать историю всех записей пользователя;
- сделать сортировку по дате;
- сделать поиск по контакту;
- сделать поиск по номеру телефона.

Поиск по дате и фильтрации по валюте в первой версии не делать.

### Шаг 8: Редактирование и удаление

- добавить редактирование записи;
- добавить подтверждение перед удалением;
- перемещать удаленную запись в раздел “Удаленные”;
- запретить редактирование удаленной записи;
- разрешить восстановление в течение 7 дней.

### Шаг 9: Очистка и архив

- добавить фоновую задачу для записей старше 7 дней в разделе “Удаленные”;
- скрывать такие записи из пользовательского интерфейса;
- хранить технический архив базы данных без пользовательского доступа;
- не показывать архивные записи обычному пользователю.

Доступ к архиву в первой версии только технический, без админ-панели.

### Шаг 10: Безопасность и логи

- хранить пароли только в защищенном виде;
- не отдавать лишние поля через API;
- проверять `user_id` во всех действиях;
- логировать вход, ошибки входа, изменение данных, создание, редактирование, удаление и восстановление записи;
- не показывать пользователю внутренние технические ошибки.

### Шаг 11: Проверка первой версии

Проверить, что пользователь может:

- зарегистрироваться;
- войти;
- восстановить пароль;
- изменить имя, фамилию, email, мобильный номер или пароль в личном кабинете;
- удалить свой аккаунт в личном кабинете после ответа на секретный вопрос;
- добавить контакт;
- создать запись;
- найти запись;
- отредактировать запись;
- удалить запись;
- восстановить запись в течение 7 дней;
- выйти из аккаунта.

### Шаг 12: Оптимизация первой версии

- добавить пагинацию для записей, контактов, удаленных записей и истории контакта;
- ограничить размер API-ответов;
- проверить индексы базы данных под основные запросы;
- сделать фоновые задачи батчами;
- проверить, что архивные записи не видны обычному пользователю;
- выполнить `npm run lint` и `npm run build`.

Подробные правила описаны в `specification/technical-specs/14-optimization.md`.

## Что нельзя добавлять во время первой разработки

В первую версию нельзя добавлять:

- реальные денежные переводы;
- платежи;
- банковские карты;
- кошельки;
- хранение денег;
- комиссию;
- статус записи;
- автоматический курс валют;
- фильтр по валюте;
- командные роли;
- сложную аналитику;
- мобильное приложение в составе первой web-версии.
