# Мобильная безопасность HunaSuna

## Назначение документа

Этот документ описывает правила безопасности для мобильного приложения HunaSuna.

Мобильное приложение использует общий backend и не должно ослаблять правила web-версии.

## Сессия

Мобильное приложение использует session token из `UserSession`.

Token передается только через:

```text
Authorization: Bearer <session token>
```

Token нельзя хранить в обычном состоянии приложения, AsyncStorage без защиты, логах, URL или crash-report тексте.

Для хранения использовать защищенное хранилище устройства, например Expo SecureStore.

## Вход и выход

После входа приложение сохраняет token в защищенном хранилище.

При запуске приложение проверяет наличие token и открывает защищенные экраны только после проверки текущего пользователя через API.

При выходе приложение:

- вызывает `/api/auth` с действием `logout`;
- отправляет bearer token;
- удаляет token из защищенного хранилища;
- очищает локальное состояние пользователя.

## Восстановление пароля

В первой версии восстановление пароля работает только через секретный вопрос и ответ.

Мобильное приложение не делает экраны для SMS-кода, email-кода или временного кода восстановления.

Секретный ответ нельзя показывать после ввода и нельзя сохранять на устройстве.

После 5 неправильных секретных ответов backend блокирует восстановление для этого IP-адреса и логина на 30 минут. Мобильное приложение должно показать простую ошибку и не пытаться обходить блокировку.

## Данные пользователя

Мобильное приложение не должно показывать данные до успешной проверки сессии.

Все запросы к контактам, записям, поиску и удаленным записям должны идти через API, который проверяет текущего пользователя.

Нельзя хранить полную копию личных данных пользователя на устройстве без отдельного решения об offline-first режиме.

## Секреты

В мобильном коде нельзя хранить:

- `DATABASE_URL`;
- `CRON_SECRET`;
- серверные ключи;
- приватные ключи;
- пароли администратора;
- любые секреты backend.

В мобильном приложении можно хранить только публичный API URL для нужного окружения.

## Сеть

Production API должен работать только через HTTPS.

Если сеть недоступна, приложение показывает простое сообщение об ошибке и не создает видимость, что данные уже сохранены.

## Ошибки

Ошибки должны быть понятными пользователю.

Мобильное приложение не должно показывать stack trace, SQL, внутренние имена таблиц, токены или технические секреты.

## Ограничения первой мобильной версии

В первой мобильной версии не делать:

- offline-first синхронизацию;
- хранение серверных секретов;
- отдельный backend;
- реальные платежи;
- банковские функции;
- удаление аккаунта пользователя.
